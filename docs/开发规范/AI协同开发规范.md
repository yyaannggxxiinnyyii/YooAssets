# AI 协同开发统一规范（给其他 AI 助手）

> 目的：让任何接入项目的 AI 在阅读本文件后，输出与本项目一致的代码风格与工程规范。

## 1. 必读文档顺序

- docs/开发规范/协同开发规范.md
- docs/开发规范/代码风格规范.md
- docs/开发规范/AI协同开发规范.md

## 2. 代码生成硬性规则

1. 所有类必须使用 `///` 中文注释，清晰说明脚本职责。
2. 所有方法（生命周期函数除外）必须使用 `///` 中文注释。
3. 可配置字段统一使用 `[SerializeField] private`，避免直接公开字段。
4. 同类字段必须按中文 `[Header("...")]` 分组，表达用途分类；用`[Tooltip("")]`描述字段 用`///`描述私有字段 详细可参考 `Assets\Scripts\Cards\Data\CardDefinition.cs` 脚本
5. 命名遵循项目规范：
   - 类/方法：`PascalCase`
   - 私有字段：`_camelCase`
   - 局部变量/参数：`camelCase`
6. 不得添加与任务无关的重构、依赖升级或大规模风格改写。
7. 对所有文件操作始终使用包含驱动器号和反斜杠的完整Windows绝对路径
8. 对文档进行写入、修改的时候分段写入，每次只写入 1~200行 不要一次性编辑过多内容 如果多次 失败就改用 bash 命令写文件

## 3. Unity 侧实现规则

1. 新功能先做最小可运行闭环，再扩展。
2. 与性能相关的组件引用优先在 `Awake/Start` 缓存。
3. `Update` 处理输入，`FixedUpdate` 处理物理。
4. 日志必须包含模块前缀，例如 `[Interactable]`、`[Loop]`。

## 4. 文档与提交规则

1. 新增系统时需同步更新对应文档（至少更新 `docs/DESIGN.md` 的系统说明）。
2. 提交信息遵守 Conventional Commits。
3. 每次改动只解决一个明确问题。

## 5. 输出风格要求（AI）

1. 输出内容简洁、可执行。
2. 明确列出修改文件与目的。
3. 不编造不存在的文件与功能。
4. 优先给出可直接落地的下一步操作。
5. 输出前先确认需求细节，遇到问题弹出问询选项卡，避免误解导致返工，例如：
   - “请确认需要实现的功能范围是仅限于周目切换，还是包括线索系统和结局判定？”
   - “请提供一个示例线索的字段定义，以确保我理解正确。”
6. 开始任务之前 列任务清单，完成一个清单项等待检验通过后，再继续下一个，确保每一步都符合规范要求。
